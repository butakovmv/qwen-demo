# Требования

## Соглашения по архитектуре и разработке проекта

1. Стремимся к Low Coupling (низкая связанность) и High Cohesion (высокое зацепление), стараемся ограничивать видимость классов где, это возможно. 

2. Контролируем SOLID

3. Придерживаемся гексагональной архитектуры b Domain Driven Development, изолируем домены друг от друга и от адаптеров.

4. Операции в модуле `operation` описываются только интерфейсами. Одна операция - один интерфейс, с одним методом, который принимает единственный агрегирующий аргумент и возвращает единственный агрегирующий результат. Интерфейсы метода объявляются вложенными в интерфейс операции рядом с объявлением метода.

5. Используем много профилей Spring. Цель - запускать приложение, независимо указывая профили, меняющие поведение отдельных модулей, с помощью профилей добавлять или удалять feature-toggle.

## Области видимость

| Класс | Видимость | Обоснование |
|---|---|---|
| **Application / main** | `public` (по умолчанию) | Точка входа, должна быть видна |
| **Интерфейсы operation** (`interface`) | `public` (по умолчанию) | Публичный контракт операций, которые будут вызываться или реализовываться в других модулях |
| **DTO** (`data class`) | `internal` | Особенности контракта адаптера нужны только в этом модуле |
| **Мапперы** (`@Component class`) | `internal` | Особенности преобразования из/в интерфейсы предметной области нужны только в этом модуле |
| **Реализации operation** (`@Component class`) | `internal` | Внутренняя деталь, внешний код зависит от интерфейса |
| **Контроллеры** (`@RestController class`) | `internal` | Spring обнаруживает через reflection, извне не вызываются |
| **Конфигурации** (`@Configuration class`) | `internal` | Внутренняя настройка модуля |
| **Параметры конструкторов** | `private val` | Зависимости не должны утекать наружу |
| **Вспомогательные функции/классы** | `private` / `internal` | Минимально необходимая видимость |

### Тестирование БД

Тесты `postgres/` должны использовать генераторы, которые создают случайные тестовые сущности, с которыми будет работать тест, и сразу сохраняют их в БД:

- **`QuestionGenerator`** — генерирует `QuestionEntity` и вставляет через `INSERT INTO`
- **`AnswerGenerator`** — генерирует `AnswerEntity` для заданных вопросов и вставляет

Каждый тест вызывает `createAndInsert()` в `@BeforeEach`, а `@AfterEach` очищает все таблицы.

После прогона тестов `postgres/` автоматически удаляются временные файлы H2-базы (`r2dbc:h2:mem:`) через задачу `doLast` в `tasks.test`.
